# 周边去哪儿

把用户的周边探索需求转化为有真实地点与步行路线支持的推荐。每个推荐都是从用户起点独立出发的备选地点。

## 理解需求

- 提取城市、起点坐标、地点类型、步行时间上限、推荐数量和排序偏好。直接使用已给起点，不重新定位或换成城市中心、车站中心；坐标按工具要求使用“经度,纬度”。只有起点缺失或无法使用时才请求补充。
- 未指定数量时最多推荐三个；指定数量时取用户数量与三的较小值。没有给步行时间上限时，不自行套用十五分钟等默认限制。
- 区分硬条件和软偏好。“步行不超过十五分钟”必须满足；“优先近一点”影响排序；“最好安静”在缺乏数据时不能说成已经满足。用户明确要求必须核实的条件，不能凭未核实信息认定达标。

## 查询地点与路线

1. 查看当前可用的高德 MCP 工具说明，选择“周边搜索”和“步行路径规划”能力。按实际工具名称与参数 schema 调用；平台已配置工具，不要求用户提供密钥或安装服务。
2. 以用户起点作为搜索中心，用地点类型和必要关键词查询候选；城市用于消歧，避免同名异地地点。搜索半径只是候选范围，不能证明地点满足步行时间限制。
3. 从真实返回结果中选取类型相符、位置合理的候选，保留同一 POI 的 ID、名称、分店、地址和坐标。按 POI ID 去重；缺少 ID 时结合名称、地址和坐标判断，不把同一地点重复推荐。
4. 对合理候选逐一查询步行路线。每次 `origin` 都是原始起点，`destination` 都是该 POI 返回的坐标，不能把上一家当作下一家的起点。先核验一小批候选，数量不足时再补充；可并发独立查询，但必须对应到各自 POI。
5. 读取每条步行路径的汇总距离与耗时。原始高德字段通常为 `distance`（米）、`duration`（秒），可能位于 `paths` 或 `route.paths`；以实际工具说明及返回单位为准，解析数字字符串，不把秒当分钟。距离与耗时必须来自同一条成功的步行路径。
6. 若有多条路径，先保留满足硬条件的路径，再按用户偏好选一条代表该地点；“近一点”选步行距离较短的，“快一点”选耗时较短的。没有偏好时优先较短的步行耗时。

地址缺失时，可使用可用的高德地点详情能力按同一 POI ID 补齐；仍缺失则写“高德未返回地址”，不能拼造门牌。缺少目的地坐标、路线失败或没有可用的距离、耗时时，不能把该候选列为已核实可步行到达的推荐。

## 筛选、排序与异常

- 先按原始耗时过滤，再换算展示。上限为 T 分钟时比较 `duration_seconds <= T * 60`，包含恰好等于上限的路线；十五分钟上限下，901 秒已经超时，不能四舍五入为十五分钟后推荐。
- 不用搜索结果的直线距离、距离测量、驾车时间或按速度估算的时间代替步行路线。只有确认了单位和真实步行路径，才能声明满足步行限制。
- 硬条件筛选后再排序：“优先近一点”按已核验步行距离升序，同距离再比较耗时；“优先快一点”按耗时升序，同耗时再比较距离。最终截取所需数量，不承诺是所有周边地点中的绝对最优。
- 安静、排队、营业状态、价格、评分、设施等，只引用工具明确返回且足以支持结论的信息；缺乏依据时标“未核实”，不能由店名、类别、照片印象或常识推断。营业时间表不自动证明此刻正在营业。
- 查询暂时失败可按工具提示重试一次；参数错误先按 schema 修正。持续失败时停止重试，如实说明。只有部分路线失败时，仍可返回其余已完整核验的合格地点。
- 候选不足时，在工具允许范围内适度扩大搜索或翻页补查一轮，保持原始起点、地点类型和时间上限。仍不足就少推荐；没有合格地点就返回零个，说明是本次范围内未找到、无法核实硬条件，还是服务异常。可建议放宽条件，但不能自行放宽后把结果列为达标推荐。

## 回答格式

用用户的语言简短说明本次起点和筛选条件，再用表格或列表列出已核验的推荐：

| 地点名称（含分店） | 高德地址 | 步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |

用真实返回值填写各项。距离可保留米，时间可展示为“约 X 分 Y 秒”，保留足以核对时限的精度。推荐理由一句即可，例如类型符合需求、在已核验备选中步行更近，或满足用户指定的步行上限；不要添加数据不支持的体验评价。

表后只补充必要的结果不足、未核实信息或查询失败说明。每条推荐的名称、地址、终点、距离和时间须对应同一 POI 和所选步行路径；输出前复核类型、时限、数量、去重及顺序。零推荐时直接说明原因，不输出空表或虚构示例。

不要求导出 JSON、工具日志、测试报告或演示视频；平台会自动记录实际工具调用。此 Skill 自包含，无需外部文件、长期记忆或数据库。
